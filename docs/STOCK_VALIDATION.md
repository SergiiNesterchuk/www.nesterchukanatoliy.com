# Stock validation

Як обмежується кількість товару в замовленні. Пов'язано: [CHECKOUT.md](CHECKOUT.md)

**Принцип: frontend = UX, backend = source of truth.**
Frontend лише не дає користувачу зробити явно неможливе. Гарантію дає сервер.

---

## Три рівні

### 1. Каталог / кошик

`components/cart/AddToCartButton.tsx` кладе в кошик поле `maxQuantity`:

```ts
maxQuantity: product.quantity ?? MAX_CART_QUANTITY   // null залишок → стеля 99
```

`hooks/useCart.ts` обмежує при повторному додаванні того самого товару:
`Math.min(existing.quantity + qty, maxQuantity)`.

`CartDrawer` → `CartItem` → `QuantitySelector max={item.maxQuantity ?? 99}` — кнопка `+`
disabled при досягненні максимуму.

⚠️ `useCart.updateQuantity()` **не має** власного обмеження — його накладає UI. Якщо
викликаєте `updateQuantity` з нового місця, обмеження треба передбачити там.

### 2. Checkout

`components/checkout/CheckoutForm.tsx` має власну верстку `−`/`+` (не `QuantitySelector`).
Саме тут раніше був баг: кнопка `+` ігнорувала `maxQuantity`, і при залишку 2 можна було
виставити 20. Виправлено — той самий `item.maxQuantity` тепер читається і тут.

Додатково при відкритті `/checkout` **один раз** викликається `POST /api/cart/validate`
(`app/api/cart/validate/route.ts` → `services/CartService.ts`). Ендпоінт існував у проєкті,
але до цього не мав жодного виклику з фронтенду. Що з нього береться:

| Поле відповіді | Використання |
|---|---|
| `stockAvailable` | актуальна стеля для кнопки `+` (пріоритетніша за `maxQuantity` з localStorage) |
| `quantityAdjusted` + `quantity` | застаріла кількість підрізається до доступної через `updateQuantity` |
| `errors[]` | повідомлення «‹Товар› — доступно лише N шт.» під підсумком |

Поведінка UI:

- `+` disabled при `quantity >= maxQty`, поряд підказка «макс. N шт.»;
- `−` лишається активною;
- перед submit `validate()` ще раз звіряє `quantity <= maxQty`.

**Fail-open:** якщо `/api/cart/validate` недоступний, checkout не блокується — сервер
усе одно перевірить при створенні замовлення.

### 3. Backend (authoritative)

`services/OrderService.ts`, у циклі підрахунку `subtotal`:

```ts
if (product.stockStatus !== "in_stock") throw new ValidationError(`"${product.name}" немає в наявності`);
if (product.quantity !== null && product.quantity < item.quantity) {
  throw new ValidationError(`"${product.name}" — доступно лише ${product.quantity} шт.`);
}
```

Перевірка стоїть **до** створення `Order`, платіжної сесії, синхронізації з KeyCRM і
списання залишків. Відповідь — **HTTP 400 / `VALIDATION_ERROR`**, побічних ефектів немає:
замовлення не створюється, залишок не змінюється.

Це захищає від:

- застарілого `localStorage` (кошик міг пролежати тижні);
- прямого API-запиту в обхід UI;
- гонки між покупцями (див. нижче).

Списання залишків відбувається **після** створення замовлення, у тому ж
`OrderService.createOrder()`.

## Known limitations

**Reservation system немає.** Товар не резервується ні при додаванні в кошик, ні при
відкритті checkout. Два покупці можуть одночасно тримати в кошиках останню одиницю —
замовлення створить той, чий запит дійде до сервера першим, другий отримає 400.

Це свідоме рішення: резервування потребувало б окремої сутності з TTL, фонового
звільнення прострочених резервів і зміни логіки списання. Для поточних обсягів надлишкове.

**Frontend не гарантує актуальність.** `/api/cart/validate` дає зріз на момент відкриття
сторінки. Між ним і натисканням «Оплатити» залишок міг змінитись — це нормально й
покривається серверною перевіркою.

**Списання не транзакційне з перевіркою.** Перевірка залишку і його списання — окремі
кроки, не в одній транзакції з блокуванням рядка. За високої паралельності теоретично
можливий овердрафт. Для поточного трафіку ризик низький; закриття потребувало б
`SELECT ... FOR UPDATE` або атомарного `decrement` з умовою.

---

## Що перевіряти при змінах

- будь-який новий UI зміни кількості має читати `maxQuantity`, а не покладатись на бекенд;
- серверну перевірку в `OrderService.createOrder()` не послаблювати й не виносити в route;
- сценарій «залишок 2, прямий API з `quantity: 20`» має давати 400 і не створювати замовлення.
