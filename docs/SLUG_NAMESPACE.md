# Public slug namespace

Як влаштований спільний URL-простір `/{slug}` і чому однаковий slug у різних сутностей — проблема.

---

## Хто живе в `/{slug}`

Root-неймспейс `/{slug}` ділять **три** сутності:

- `Category`
- `Product`
- `Page`

`BlogPost` **не входить** — він резолвиться через `app/(store)/blog/[slug]/page.tsx`, тобто
живе під `/blog/{slug}`, окремий простір. Однаковий slug у блог-посту й товару колізії не дає.

## Routing priority

`app/(store)/[slug]/page.tsx`, функція `resolveSlug()` перевіряє в жорсткому порядку:

```
Category  →  Product  →  Page
```

Перший збіг виграє, решта не перевіряється. Якщо збігу немає — шукається активний
`Redirect`, інакше `notFound()`.

**Наслідок колізії:** категорія завжди перекриває товар із тим самим slug. Реальний випадок —
категорія «Груша» (`hrusha`) і товар «Груша 1кг» (`hrusha`): `/hrusha` віддавав сторінку
категорії з HTTP 200, а товар ставав недосяжним. Це не 404 і не помилка рендеру, тому
діагностується неочевидно — сторінка «відкривається», просто не та.

## Чому це було можливо

Prisma `@unique` на `slug` стоїть **окремо в кожній таблиці** (`Category`, `Product`, `Page`,
`BlogPost`). Крос-табличного DB-констрейнта немає й бути не може без зміни схеми.
Адмінка ж перевіряла унікальність лише в межах своєї таблиці.

---

## Guard: `shared/slug-namespace.ts`

Єдине джерело логіки, підключене до всіх шести admin-роутів
(`products`, `categories`, `pages` × create/update).

| Функція | Відповідальність |
|---|---|
| `findSlugOwner(slug, self?)` | хто зайняв URL у namespace; повертає `{type, name}` або `null`; `self` виключає поточний запис |
| `assertSlugAvailable(slug, self?)` | кидає `ValidationError` (400) з назвою власника |
| `getUniquePublicSlug(base, self?)` | перший вільний варіант: `base`, `base-2`, `base-3`, … |
| `isAutoSlug(body)` | чи slug згенеровано автоматично |
| `resolveSlugForCreate(slug, auto)` | обирає одну з двох стратегій нижче |

### Auto vs manual

Адмінські форми (`ProductEditForm`, `CategoryEditForm`) уже тримали стан `slugManual`:
при створенні slug автозаповнюється з назви через `generateSlug()` (`shared/slug.ts`), а
щойно користувач торкається поля — стає manual. При редагуванні завжди manual.
Цей прапорець передається на сервер прихованим полем `slugAuto`.

**Auto** — сервер сам зсуває на вільний варіант, без помилки:

```
Category «Груша»  → /hrusha
Product  «Груша»  → /hrusha-2      (автоматично)
Product  «Груша»  → /hrusha-3      (наступний)
```

Без хешів і UUID — URL лишається читабельним. Ліміт пошуку — 200 спроб, далі помилка з
проханням вказати slug вручну.

**Manual** — введене вручну значення **ніколи не підміняється мовчки**:

```
HTTP 400  VALIDATION_ERROR
"URL /hrusha вже використовується категорією «Груша». Вкажіть іншу адресу."
```

Повідомлення завжди називає тип і назву сутності, яка займає URL.

**Відсутній прапорець** трактується як manual — безпечний дефолт для зовнішніх звернень
до API: краще помилка, ніж тиха підміна.

### Edit

`self` виключає запис із перевірки самого себе — збереження товару без зміни slug працює
нормально, false-positive немає. Зміна на slug, зайнятий **іншою** сутністю, блокується.

### Назви не обмежуються

Обмежується **лише slug**. Три сутності з display name «Груша» спокійно співіснують —
проблема була в URL, не в назві.

---

## Що це НЕ робить

- **не перейменовує існуючі дані** — guard діє тільки на нові записи й майбутні редагування;
  наявні URL лишаються як є;
- **не створює редиректів** автоматично — якщо міняєте slug опублікованої сторінки,
  додайте редирект вручну в `/admin/redirects`;
- **не чіпає `BlogPost`**.

---

## Known limitation: race condition

Крос-табличного DB unique constraint немає, тому перевірка — application-level. Два
паралельні create теоретично можуть обидва побачити slug вільним і обидва записатись,
відтворивши колізію.

- для адмінського інтерфейсу з одним-двома користувачами ризик низький;
- наслідок не гірший за стан до guard'а;
- повне закриття потребувало б спільної таблиці `Routes` з унікальним індексом, advisory
  lock або іншої зміни архітектури — свідомо не реалізовано.

## Якщо колізія все ж виникла

Це проблема **даних**, не коду. Виправляється зміною одного slug в адмінці:

1. знайти обидві сутності з однаковим slug;
2. змінити менш важливу (зазвичай товар → `<slug>-2`);
3. за потреби додати редирект зі старої адреси.
